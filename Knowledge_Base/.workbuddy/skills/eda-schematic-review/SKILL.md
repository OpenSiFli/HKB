# EDA 原理图 PDF 评审

## 目的

将一份 EDA 导出的原理图 PDF（Altium/KiCad 等矢量导出）自动解析为结构化文本，
并依据硬件知识库中的设计校验规则（CR_*）逐项比对，产出一份带风险分级的评审报告
（Markdown 源 + 排版后的 PDF）。流程忠实遵循项目内 `EDA原理图PDF识别提示词.md` 的「方案A 优先」原则。

> **本技能随知识库一起存放于 `.workbuddy/skills/eda-schematic-review/`**。
> 知识库（含 `wiki/` 校验规则与 `references/` 方法文档）整体拷贝到其他机器后，
> WorkBuddy 会在该项目下自动发现并加载本技能，无需任何机器专属配置。

## 何时使用

- 用户要求评审某份原理图 PDF（常带 `@文件路径`）。
- 用户明确要求「按 EDA原理图PDF识别提示词.md 的方法」。
- 用户需要「对照知识库校验规则审图」「投板前 checklist」。

## 评审模式（训练 / 正式评审）—— 必须先判定再执行

流程开始前，先根据用户**本次输入**判定模式；两种模式输出的报告内容差异如下：

- **训练**（用户请求中出现「训练」二字，如「训练一下」「按训练模式评审」「训练这份图」）→ 保留现有详细方式。
- **正式评审**（用户请求中**未出现「训练」**）→ 默认模式，按交付级正式评审输出。

### 训练模式（方法调试 / 规则演练用）
报告保留全部细节，便于核对提取与判读是否准确：
1. 含「评审方法与数据源」整节：方案A/方案B 提取、工具（pdfplumber）版本、提取记录数与分类、坐标级复核脚本与定位过程、DNP 判读方法等「如何识别与提取」的全部内容。
2. checklist 按知识库演变呈现：可标注 CR_Checklist_* 系由官方 Checklist 转化、规则总数为当前条数，并保留「相较历史版本新增 / 调整」的说明。
3. 适用：验证提取脚本、规则命中逻辑、坐标消歧是否正确。

### 正式评审模式（交付硬件工程师 / 投板前结论）
报告**严格收敛为评审结论本身**，须满足三条硬性约束：
1. **不得包含「识别与提取方法」类内容**：删除「评审方法与数据源」整节，以及一切方案A/B、pdfplumber、坐标定位脚本、提取记录数、DNP 判读方法等表述。报告只写「依据哪条规则、**发现什么问题**、**结论与整改建议**」。
2. **checklist 以当前知识库总条目为准，不区分历史版本**：
   - CR_Checklist_* 直接枚举 `wiki/mcu/all/check_rules/` 下当前**全部** `CR_Checklist_*.md`（当前共 13 条），不再写「新增 / 相较旧版 / 历史版本」等表述。
   - 规则总数一律取当前知识库实际条数（当前 41 条 = 21 CR + 7 CR_RefDesign + 13 CR_Checklist），不引用历史版本计数。
   - 摘要 / 结论中不出现「相对 v2/v3 修正」这类历史对比叙述（除非用户明确要求对比）。
3. **输出内容净化（2026-10-16 起强制）—— 报告里不出现任何「报告规范 / 方法论 / 过程性」内容**：
   报告是给硬件开发者看的结论性文件。下列内容一律**不写入报告文件**，只在对话中向用户说明：
   - **YAML frontmatter**：不输出 title / type / aliases / tags / sources / mcu_family / mcu_model / hardware_version / created / updated 等元数据（`md2pdf_report.py` 已同步在转 PDF 时剥离，双保险）。
   - **信息框**：不输出「评审对象 / 主控 / 评审日期 / 知识库版本 / 可视化规范」等 `>` 引用块；机型、供电版、封装信息并入「一、摘要」首句正文。
   - **写作规范注解**：不输出「信息优先级遵循规范…」「三类状态必须分开…」「表格列宽…」「状态图例：PASS／命中／待核实／N/A…」「不要把长分析装进彩色警告框」「通过项避免仅写正常」等章节注解。唯一例外：「四、规则命中总览」下的状态一行图例可保留，因其是读表所需。
   - **提取过程**：不输出方案A／方案B、pdfplumber、`extract_A.json`、`schematic_struct_text.txt`、`line <n>` 行号、坐标复核脚本、提取记录数、「合并文本歧义须坐标复核」等表述；证据直接写网络名／位号／数值，或写「图纸确认」。
   - **附录**：不输出「附录 A 排版样式规范」「附录 B 证据图与防视觉误导规范」；排版与证据规范实体见 [[硬件评审报告排版与UI规范_V1.0]]。
   - 章节编号固定为：一 摘要 → 二 阶段结论 → 三 问题总表 → 四 规则命中总览 → 五 问题详情 → 六 投板前待闭环清单 → 七 结论 → 八 关联页面与参考文档。

## 流程

### 步骤 1：提取（方案A，优先）

运行 `scripts/extract_schematic.py <input.pdf> [output_dir]`（**必须显式传入 PDF 路径**，无机器专属默认路径）：

- 用 pdfplumber 读取 `page.chars`，保留坐标/字号/字体。
- EDA 正则筛选：位号（`R/C/U/L/D/Q/T/P...`）、元件参数（阻值/容值/电压）、网络标号、电源地。
- 输出 `extract_A.json`（结构化记录，字段含 page_num/extract_scheme/type/content/x/y/confidence/status）
  与 `schematic_struct_text.txt`（按页、按 `(top,x)` 排序，便于全文检索）。

**方案判定**：任一页 `chars < 30` 即标记该页需切换「方案B OCR」（PaddleOCR 等栅格兜底）。
绝大多数矢量导出 PDF 方案A 即可成功，无需方案B。

**元件属性判读（预留 / 不焊接）**：提取元件时，若元件属性或图纸标注含 `DNP` / `NC` / `NF`，
或立创EDA（LCEDA）中该器件被标记为**灰色（未放置 / 未启用状态）**，均表示**预留器件、不焊接（Not Mounted）**。
处理原则：
- 这类器件不计入实际装配 BOM，提取脚本应在 `extract_A.json` 记录 `status: "DNP"` 以便与已焊接器件区分。
- 对照 CR_* 规则时：若某条规则的被核查对象（如上拉电阻、负载电容、ESD 器件）标 DNP，
  则该规则对其实例判 **N/A（不适用）**，并在报告中注明「预留不焊」；**切勿把 DNP 元件当作已焊接电路去判违规或判缺件**。
- 例：CR_XTAL48M 中 48MHz 晶振两端负载电容标 DNP，需结合实际料号判断（石英晶体需焊负载电容、陶瓷谐振器可 DNP），不能简单判「缺电容」。

### 步骤 2：判定 MCU 型号与版本（最关键，先做）

读取 `references/knowledge_base_review.md` §1。从提取文本识别：

- 充电器芯片（AW32012 等）、电池网络（VBAT/BAT）、`VDD18_VOUT` 字样 → **锂电版**（523/525/527）。
- 外部 1.8V 输入 `VDD_SIP`、必须有外部 32.768kHz 晶振 → **常规版**（52A/52B/52D）。

引脚定义差异巨大，**误判会推翻整份报告**。锂电版 pin23 是 `VDD18_VOUT`（内部 LDO 输出），
非常规版的外部 `VDD_SIP`；锂电版内部 RC 可作 RTC，外部 32k 晶振可选。

### 步骤 3：对照校验规则

读取知识库 `wiki/mcu/all/check_rules/CR_*.md`（规则文件路径**相对知识库根目录**，随知识库一起拷贝），
逐条与提取出的网络/元件比对，给出状态：PASS / 命中 / 待核实 / N/A（不适用）。

规则分三类，当前共 **41 条**：
- **通用 CR_\***（21 条，分 致命/严重/一般/优化建议 四级，详见 `references/knowledge_base_review.md` §2）；
- **参考设计黄金样板 CR_RefDesign_\***（7 条，源自官方参考设计原理图）；
- **官方硬件 Checklist 转化 CR_Checklist_\***（13 条，覆盖电源/时钟/存储/射频/显示/接口/唤醒/ESD/生产/封装/功耗/调试/音频）。

高频真问题与逐项风险等级见 `references/knowledge_base_review.md` §2–§3。

**还原电路方法**：当前模型无法读取栅格图，禁止视觉核对。一律用
`grep -n "关键字" schematic_struct_text.txt` 或原始 PDF 全文检索确认某引脚/网络是否连接
（grep 全图空 = 该信号未连接，据此判 N/A）。涉及「某元件是否在 X 旁 / 属于哪个模块」的判读，
必须用 `scripts/probe_component.py` 按坐标精确定位复核（见 `references/knowledge_base_review.md` §0）。

### 步骤 4：生成报告

按「评审模式」选择对应章节骨架（亦可参考 `wiki/mcu/all/report_template/_template.md`；其视觉参数遵循 [[硬件评审报告排版与UI规范_V1.0]] V1.0，关键要求：三类状态分离＝等级 P0-P2／事实状态／处理状态；问题总表 5 列；P0 标签须同时显事实状态；绿色仅用于有证据通过或已关闭）：

- **训练模式**（章节含方法论，checklist 可标注历史演变）：
  `摘要 → 评审方法与数据源 → CR 命中总览表 → 风险分级详情 → 投板前待闭环清单（checkbox）→ 结论 → 关联页面/来源`
- **正式评审模式**（严格收敛，不含方法论、checklist 不区分历史版本）：
  `一 摘要 → 二 阶段结论 → 三 问题总表（5 列）→ 四 规则命中总览 → 五 问题详情（按 PRJ 编号）→ 六 投板前待闭环清单 → 七 结论 → 八 关联页面与参考文档`
  - 上述「输出内容净化」第 3 条同时适用：无 frontmatter、无信息框、无章节写作规范注解、无识别与提取过程、无附录。
  - 删除「评审方法与数据源」整节。
  - 总览表中 checklist 小节标题改为「CR_Checklist 规则（当前知识库共 13 条）」，逐条枚举当前 `wiki/mcu/all/check_rules/CR_Checklist_*.md`，**不写「新增 / 历史版本 / 相较旧版」**，规则总数取当前知识库实际条数（当前 41 条 = 21 CR + 7 CR_RefDesign + 13 CR_Checklist）。
  - 摘要 / 结论不出现「相对 v2/v3 修正」等历史对比（除非用户明确要求对比）。

- 用 `scripts/md2pdf_report.py --md <报告.md> --pdf <报告.pdf> --title <标题> --date <YYYY-MM-DD>` 转 PDF。
  转换器已修复大表格跨页留白 bug（页内高度阈值自动换页）。

**封面与版式（2026-10-16 起，v2 渲染器自动实现）**：
- 报告 md 顶部放 `<!-- COVER ... -->` 块（模板 `_template.md` 有现成骨架），转换器据此生成**思澈规格书风格封面**：
  左上 SiFli logo（`assets/sifli_logo.png` 自动探测，可 `--logo` 覆盖）、右侧黑主标题 + 红副题、版本/文档号、
  关键信息行（评审结论按 通过=绿 / 有条件通过=琥珀 / 不通过=红 着色）、底部「重要说明」与公司落款。
- 内容页自动带页眉（左：报告标题 / 右：评审对象）与页脚（评审日期·版本 | Confidential | 页码），封面除外。
- 正文渲染增强（无需在 md 里做任何额外标记，转换器自动识别）：
  「- **标签**：值」→ 标签卡片行；`- **整体判定**：xxx` → 彩色判定横幅；
  `**PRJ-xxx [P0 ...]**` 问题条目 → 左侧等级色条；表格按内容自动列宽、P0/P1/P2/致命/严重/一般/优化 词着色；
  `[[双链]]`、行内反引号在 PDF 中自动转为纯文本。长列表/卡片自动跨页并重复表头。
- **一/六/七/八 章一律表格化**（与 `wiki/mcu/all/report_template/_template.md` 一致）：摘要用「重点项｜等级·状态｜须执行动作」表 + 已确认 PASS 小表；闭环清单用「等级｜PRJ｜闭环说明｜状态」表（待办=琥珀／已闭环=绿）；结论用「PRJ｜等级·状态｜结论要点」表 + 整体判定横幅；关联页面用「分类｜内容」表。不用成段文字或长 checkbox 列表。

### 步骤 5：核查交付物

- 确认 PDF 页数正常（无大量空白页）；如页数异常，检查 `render_table` 的 `trigger` 阈值逻辑。
- 确保 Markdown 与 PDF 的日期/版本一致。

## 环境依赖（无机器专属路径，拷贝即用）

- **Python**：需要一个含 `pdfplumber` 与 `fpdf2` 的 Python 3 解释器。
  推荐在本机建独立 venv（可与知识库一起拷贝复用，不污染全局）：
  `<python3> -m venv venv && venv/Scripts/pip install pdfplumber fpdf2`，
  之后用 `venv/Scripts/python.exe` 运行 `scripts/` 下脚本。
- **中文字体**：`md2pdf_report.py` 默认自动探测 Windows 中文字体
  （`msyh.ttc` → `simsun.ttc` → `simhei.ttf`）；均不存在时明确报错，可用 `--font` 指定任意支持中文的 TTF/TTC。
  报告正文**禁止使用 emoji 状态符号**（微软雅黑等不含 ✅🔴🟡➖✓↔ 字形，转 PDF 会变空白方框），
  状态一律用纯文字：通过 / 命中 / 待核实 / N/A。
